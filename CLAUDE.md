# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

RehaVerse — a single-page prototype UI for an adaptive pediatric hand-rehabilitation platform ("RehaBall"). It is a static, dependency-free site: `index.html` + `style.css` + `app.js`. There is no build step, no bundler, no package.json, and no test suite — open `index.html` directly in a browser (or serve the folder statically) to run it.

Everything (state, screens, simulation engine, charts, particle FX, all 8 game levels) lives in the single `app.js` file (~3600 lines, minified/dense style — no semicolons-as-style-choice, short var names). Read `app.js` in sections by grep-ing the section header comments (`/* === ... === */`) rather than loading it all at once.

## Running / deploying

- **Local**: just open `index.html` in a browser. No install, no dev server required — **except for the level-1 camera game**: browsers refuse `getUserMedia` on `file://`, so to test hand tracking you must serve the folder (`python -m http.server 8765` → `http://localhost:8765`) or use the Vercel URL. The game detects this (`window.isSecureContext`) and says so rather than failing silently.
- **Hosting**: dual-deployed — GitHub Pages (existing) and Vercel at https://reha-verse-platform.vercel.app/ (project repo: `github.com/Tarleeyay/RehaVersePlatform`, auto-deploys on every push to `main`; `Framework Preset: Other`, no build command). Root-level `vercel.json` (mirrors `docs/vercel.json`) sets `Cache-Control`/security headers for `index.html`, `app.js`, `style.css`. The two hosts do **not** share `localStorage` (different origins) — profile data created on one won't appear on the other.
- **Graphify**: this repo has a `/graphify` knowledge graph set up (`graphify-out/`). Per user's global CLAUDE.md, treat questions about codebase structure as graphify queries first (`graphify query "..."`, `graphify path`, `graphify explain`) before grepping file-by-file — see `docs/SETUP.md` §2–3 for query examples specific to this repo.

## Architecture (app.js)

The whole app is a hand-rolled SPA with no framework:

- **State**: `S` (current screen/session UI state: `screen`, `p` (active profile), `sel`, `live`, `draft`) and `H` (trial history + `engine` for the currently loaded profile). `G` holds live game/canvas state (force, target, rAF handle).
- **Routing/rendering**: `SC` is an object mapping screen name → template function (`SC.login`, `SC.pick`, `SC.home`, `SC.game`, `SC.dash`, `SC.editor`, etc.). `render()` does `$('root').innerHTML = SC[S.screen]()` then re-renders `topbar()`. There's no vdom/diffing — every screen change is a full innerHTML replace.
- **Event handling**: fully delegated. Two document-level listeners (`click`, `input`) at the bottom of the file dispatch on `data-*` attributes in the rendered HTML (`data-go`, `data-kid`, `data-mode`, `data-level`, `data-path`, etc.) rather than binding handlers per element.
- **Persistence**: `PROFILES` (array of child profiles) is loaded/saved to `localStorage` under key `rehaverse.profiles.v1` via `loadStore()`/`saveStore()`. Falls back to `SEED_PROFILES` if storage is empty/unavailable (e.g. private browsing).
- **Adaptive engine** (`newEngine`, `updateEngine`, `DIMS`, `PRIORITY`): drives real-time difficulty adjustment. `updateEngine()` looks at the rolling mean of the last 5 trial results and steps one of `PRIORITY` dimensions (`hold_time` → `tolerance_band` → `target_force`) up or down via `stepDim()`, escalating priority once a dimension is maxed out (`maxedOut()`).
- **Simulation engine** (`simulate()`, `mulberry32()`, `loadOf()`): generates a deterministic fake trial history for a profile (seeded PRNG from `hash(p.code)`) so the dashboard/charts have data to show without a real device connected. This is prototype scaffolding, not real sensor ingestion — real hardware would come from FSR/IMU/camera per `docs/SETUP.md`'s sensing section.
- **Recommendation engine** (`recommendScores()`, `recommendMode()`, `REC_W1`/`REC_W2`): scores toy/game/hybrid mode fit from `ability`, `screenEngagement`, `attentionSpan` using fixed weights.
- **Charts/visuals**: `chartConvergence()`, `chartDifficulty()`, `radar()`, `spark()`, `heat()` render inline SVG/canvas from trial history — no charting library. `FX` is a canvas particle system for game-screen rewards (bursts, rings, sparks), driven by its own `step()`/`draw()` loop.
- **Editor**: `openEditor()` / `SC.editor` + `edPreview()` let a caregiver create/edit a child profile (`data-path`-driven inputs write into `S.draft` via `getPath`/`setPath`).

## Playable games

All 8 levels are playable in Game Only (plus level 2 in Toy + Game); Toy Only and the remaining Toy + Game modes still render as "ยังไม่เปิดในต้นแบบนี้". Playability is declared **in the data**, not in the router: `LEVELS[].modes[].playable` gates the button, and `LEVELS[].modes[].screen` names the screen to route to (absent ⇒ `'game'`). Adding a third game means adding those two fields plus an `SC.<name>` / `mount<Name>()` pair and a line in `paint()`.

- **Level 1 — Shape Match (`SC.shape` / `mountShape`)**: camera hand-tracking. Reach to a shape, close your hand to grab, drag it to the matching slot, open your hand to drop.
- **Level 2 — Bubble (`SC.game` / `mountGame`)**: one scene serving **two modes**, differing only in where the force number comes from — `gameByHand()` (i.e. `S.p.mode==='game'`) is the switch.
  - *Game Only ("Bubble Pop")*: `G.target = HT.hand.close * 100`. The camera layer, status panel and privacy note only render in this mode. If the hand leaves frame the force **decays** rather than dropping to zero, so a child who drifts out of view doesn't lose the bubble instantly.
  - *Toy + Game ("Bubble Rescue")*: unchanged mouse-drag simulation standing in for the real FSR ball. No camera is opened at all — `camScreen()` is mode-aware precisely so this mode doesn't leave the webcam running.

- **Level 3 — Rocket Simulator (`SC.rocket` / `mountRocket`)**: closure drives rocket **altitude** directly, and hoops scroll past at the target altitude. Squeezing hardest flies you over every hoop, which is the entire point of the level ("คุมแรงให้อยู่ในช่วงที่กำหนด ไม่ใช่บีบให้แรงที่สุด") — verified in test, closure 1.0 scores `GES 0%` and fails. All three of the level's declared dims map to something visible: `target_force` → lane height, `tolerance_band` → hoop opening, `hold_time` → **number of hoops in a gate** (`hoopsFor()`), so a longer hold is literally a longer tunnel. One gate = one trial; it passes at ≥75% of hoops so a single wobble isn't fatal. Uses `H.engine`/`H.trials` with the same schema as level 2 — it is a force-control task, so those metrics genuinely apply (unlike level 1's reach task, which is why that one is separate).
  - **Gate height is randomised per gate (`pickAlt()`), not fixed at `target_force`.** With a fixed height the child finds one hand posture and freezes it, which trains holding, not grading — the opposite of this level. Gates are drawn ±24 around `target_force`, forced ≥15 apart from the previous one, and clamped so the whole hoop stays on screen. `target_force` still anchors the range, so the engine's adaptation still moves the whole spread.
  - Consequently the trial is **scored against `gate.alt`, not `diff.target_force`** — GAS/GES against the engine's centre would be wrong for every gate that isn't dead centre. Each trial records the `alt` it was actually asked for.
  - The lane band eases toward the incoming gate's height (`R.laneAlt`) rather than snapping. A gate takes ~4 s to cross the screen, so the lane shows the child where to fly *before* the hoops arrive; the hit test always uses the gate's true altitude, never the eased lane.

- **Level 4 — Feed Monster (`SC.monster` / `mountMonster`)**: open hand = open mouth. One trial is **two beats** — stay closed while the food flies in, *open in time* to catch it, then *close in time* to chew — because the level's goal names both ("บีบให้ทัน และปล่อยให้ตรงเวลา"). `react_window` is the tolerance for each beat, `target_size` the food size, `reps` the round length.
  - **The `armed` flag is what makes this a timing task rather than a posture task.** It only sets while the hand is *closed before the window opens*, and the catch additionally requires a fresh closed→open transition *inside* the window. Without it a child could hold their hand open and let food drift in. Verified: hand held open scores 0, hand held closed scores 0, correctly-timed play scores 4/4, and catching without chewing scores `caught 4 / ok 0`. If you change this logic, re-run those four strategies — they are the level.
  - Travel time is randomised (2.0–3.4 s) so the beat can't be counted in advance.
  - Timing metrics (`rtOpen`/`rtClose`) are not force metrics, so like level 1 this keeps its own engine (`H.timing`, `PRIORITY_TIMING`) and its own `TM.trials`, and leaves `H.trials`/`H.engine` alone.

- **Level 5 — Magic Garden Lite (`SC.garden` / `mountGarden`)**: hand *shape*, not force. A target pose is shown as a procedural glyph (`poseGlyph()`), the child's real hand is drawn beside it as a live skeleton from the landmarks (`handSkeleton()`), and holding the right shape for `hold_time` grows a plant. `contact_zones` is **how many poses are in the deck** (`POSE_ORDER.slice(0, n)`) — more poses means more of the hand must be used, which is the level's goal ("กระจายแรงรอบมือ"); `reps` is the round length. Own engine (`H.garden`, `PRIORITY_GARDEN`), own trials, force data untouched.
  - `poseOf()` classifies from per-finger extension plus splay. Extension is measured as **distance from the wrist**, not joint angle, so it survives hand rotation; the thumb gets its own test (`d(4,17)/palm`) because it abducts sideways rather than pointing with the others.
  - **Splay is auto-calibrated per child (`cal.shi/slo`), same pattern as closure.** Raw adjacent-fingertip spacing over palm size only spans about 0.18–0.40 on a real hand and shifts with hand size, so fixed thresholds misfire constantly. Calibration only updates while all four fingers are extended — splay is meaningless in a fist. Poses are debounced over 5 frames; a single glitch frame does not flip the reported pose (tested).
  - The `pinch` rule requires the index to be **curled**, for the same 2D-projection reason as level 1: a tilted open hand puts the thumb on top of the index and would otherwise read as a permanent pinch.
  - `open`/`fist` are first in `POSE_ORDER` deliberately — they need no splay threshold at all, so the earliest rounds work before calibration has seen the child's range.
  - Synthetic-landmark tests (`scratchpad/pose.js` style) cover all 8 poses. **Model a curled finger correctly if you write more**: the tip folds *back toward the palm* (closer to the wrist than the PIP). Modelling it as merely a short straight finger makes every fist read as an open hand and will send you chasing a non-existent bug in the classifier.

- **Level 6 — Treasure Runner (`SC.trek` / `mountTrek`)**: reach again, but the opposite emphasis from level 1. Level 1 trains grasp/release in a small workspace; this one trains **movement amplitude**, so the gem spawns on one of 8 perimeter anchors and the chest is always placed at the **opposite anchor** (`(i+4)%8`). Every trial is therefore a full cross-screen sweep — measured min reach 378 px on a 640-wide stage, and a dashed midline is drawn so the crossing is visible. Trials record `reach` and `crossed` (did the hand path actually cross x=320), which are the metrics that matter here and have no equivalent in level 1. Own engine (`H.trek`), separate from `H.reach` so the two reach levels don't share difficulty.
  - Spawn sector is **picked at random from the allowed set, avoiding the previous one** — not `i % n`. A strict cycle at `directions: 2` gives A,B,A,B and the child learns to pre-position instead of searching for the target. Same mistake was fixed in level 3's gate heights.

- **Level 7 — Cooking Story (`SC.cook` / `mountCook`)**: a **sequence** of wrist actions, the only level driven by rotation. `COOK_ACTS` holds six actions ordered easy→hard (`grab, open, lift, pour, stir, shake`); `directions` is how many are in the deck, `reps` the recipe length, `hold_time` scales the requirement for *every* kind (hold duration, degrees stirred, or reversal count).
  - **Rotation comes from `dist(5,17)` angle, not MediaPipe's `z`.** The palm-axis angle (index MCP → pinky MCP) is directly visible in 2D; `z` is relative and noisy. `HT.hand.roll`/`rollDelta` are unwrapped across the ±180° seam, and `rollRaw` resets to `null` whenever the hand re-enters frame — without that, re-acquisition registers as a sudden hundreds-of-degrees spin and instantly completes a stir.
  - Rotation actions measure **change from the value at step start** (`CK.roll0`), never an absolute angle, so the child can begin from any hand orientation without being asked to "zero" their wrist first.
  - **`lift` is the exception and is deliberately absolute** (`hand.y <= .32`). It was written relative to step-start position first, and that is a trap: a child whose hand is already raised when the step begins would have to lift *further*, past the top of the tracked region, and could never complete it. Tests caught this.
  - There is a **floor of `hold_time*600` ms per step**. `shake` scores on direction reversals, and without a time floor a few frames of detector jitter satisfied it in ~200 ms.
  - Mouse/keyboard fallback is press-and-hold for every action — there is no mouse equivalent of wrist rotation, and pretending otherwise would be worse than an honest substitute.

- **Level 8 — Adventure Island (`SC.quest` / `mountQuest`)**: the finale, and deliberately **introduces no new mechanic**. It replays the core of levels 1–7 as short stations: `reach` (L1/L6), `hold` (L2/L3), `beat` (L4), `shape` (L5), `turn` (L7). This is the only level that uses **all five** of its declared dims — `target_force` and `hold_time` for the hold station, `target_size`/`directions` for reach, `reps` for the run length — so `PRIORITY_QUEST` covers four of them and `reps` sets length. `tolerance_band` isn't declared for this level, so the hold band is fixed at `QS_BAND` rather than silently adapting something the caregiver card doesn't show.
  - **Never draw `open` for the shape station** (`QS_POSES` excludes it). A resting hand already classifies as `open`, so that station passed with the child doing nothing — which corrupts the endurance reading this level exists to produce. Caught by the "ignore every station" test, which must score 0/N.
  - The `beat` station reuses level 4's `armed` idea: the hand must be closed before the window, so holding it open through the whole run fails.
  - Stations run back-to-back with only a short beat between them; the trail across the top is the endurance cue.

### Shared hand cursor

`handCursor(stage)` + `paintHandCursor(...)` own all reach-game input: camera → keyboard → mouse priority, whichever was used last wins, EMA smoothing, and the `waiting` flag for "camera on but no hand yet". Levels 1 and 6 both use it — **don't re-inline this logic into a new game**, the two copies will drift. `window.pointerup` is bound once at module level into `PTR_DOWN` rather than per-game `bound` flags.

### Progression / the roadmap lock

`SC.home` only lets a stop be selected when `n <= p.level + 1`, so **`p.level` is the gate on everything**. Until this was added nothing ever incremented it, which meant the seeded profiles were permanently stuck at whatever level their record said (profile 1 sits at `level: 2`, so levels 4+ were unreachable no matter how well you played).

`goReward()` is now the single exit from every round — the `data-go="reward"` handler and the programmatic `endRound()` of levels 1 and 4 all funnel through it. It unlocks the next level when the child got **at least one success** at or beyond their current level, then `saveStore()`s. The bar is deliberately that low, to match the reward screen's own promise ("เล่นจบได้เมล็ดพันธุ์เสมอ ไม่ว่าคะแนนจะเป็นเท่าไร") — this is a rehab tool, not a game to be gated behind mastery. Quitting with zero successes does not unlock; replaying a cleared level does not push you further; level 8 caps. Toy mode has no on-screen result to judge, so finishing counts as a pass or those profiles could never progress.

`S.unlocked` drives the banner on the reward screen and is reset on every `goReward()` call, so it never leaks into a later render. For demos you can still jump straight to any level with the `level` slider in the caregiver editor.

Each playable screen picks its engine in `SC.home` (`shape`→`reachEngine()`, `monster`→`timingEngine()`, else `H.engine`) and builds the `mono` debug line from that engine's own dims. Add a branch there when adding a level, or the caregiver card will show the wrong numbers.

Shared camera UI lives in `camPanel(panel, help, fallbackHint)` and `paintHandChip(label)`; don't duplicate it into a fifth game. `paint()` clears `HT.onstate` on **every** render (it closes over the outgoing screen's DOM) and calls `HT.stop()` whenever `camScreen()` is false.

**Trials must not tick while the camera panel is up.** Both loops check `#camstate.classList.contains('on')` and, while it is, keep pushing their start timestamp forward (`G.tStart` / `SH.t0`) and skip the trial block. Without this, the 14 s / 24 s timeouts elapse behind the permission dialog and log failures the child never had a chance at — which then drags the adaptive engine down before the first real attempt.

### Hand tracking (`HT`, `HT_CFG`)

MediaPipe Tasks Vision `HandLandmarker`, loaded by **dynamic `import()`** of an ESM bundle from jsDelivr (app.js is a classic script, so a static `import` is not an option). **There is no API key and no account** — the model runs entirely in the browser and no frame is recorded or transmitted. URLs live in `HT_CFG` and are overridable via `window.REHAVERSE_CONFIG.handTracking` declared before `app.js` loads, so a closed hospital network can self-host without editing the file. The model is ~7.8 MB on first load, then browser-cached.

- **Grab/release is derived, not a landmark.** `HT.read()` divides every distance by palm size (`dist(wrist, middle-MCP)`) so the numbers hold as the child moves nearer or further from the camera. Closure is a four-finger curl ratio (mean fingertip-to-wrist distance ÷ palm). All tuning lives in one `GRIP` object.
- **The absolute range is auto-calibrated per child (`HT.cal`), and this is not optional.** Fixed reference values are what make the object impossible to release: a tilted hand or a child who can't fully extend never crosses the "open" threshold, so the grab latches forever. `cal.hi/lo` seed from the child's *first observed pose* (± half `minSpan`), then expand instantly and contract very slowly (0.0006/frame). **Do not re-introduce a hard-coded initial guess** — a guess that is too wide can never contract fast enough to correct itself (the old `mid`-gated version could not lower `cal.hi` at all, which pinned closure at 1.00).
- **Decisions are relative as well as absolute.** Release fires on `close < releaseAt` **or** `close < peak − openDrop`; grab on `close > grabAt` **and** `close > trough + closeRise`. The relative arm is what serves CP hands: a child who only closes to 0.5 and relaxes to 0.25 never crosses an absolute threshold, but the *change* is unmistakable. Release is deliberately biased easier than grab — an object you can't let go of ends the session faster than one that slips.
- **No thumb–index pinch term.** It was tried and removed: the landmarks are 2D, so a hand tilted toward the camera projects the thumb on top of the index and the pinch score saturates at 1.00 with the hand wide open — a permanent phantom grab. This level trains whole-hand open/close anyway, so one clean signal beats two noisy ones. `scratchpad/grip.js`-style synthetic-landmark tests cover six hand types; re-run them before touching `GRIP`.
- **Dwell-to-drop is the safety net.** Hovering a held shape over the correct slot for 1.6 s drops it automatically and marks the trial `assisted:true`. It is deliberately much slower than a real release so hand release stays the primary path, and the flag keeps the record honest — an assisted placement is not evidence the child can release.
- **The cursor is smoothed but the metrics are not.** `hand.x/y/close` are EMA-filtered for playability; `hand.rawx/rawy/rawc` keep the unsmoothed values, because smoothing away tremor before you measure it would falsify the clinical signal.
- Only the middle of the frame (`0.20–0.80` x, `0.16–0.84` y) maps to the play area, so a child with limited range of motion never has to reach the edge of the image. The x axis is mirrored to match the mirrored video.
- `HT.stop()` releases the camera. It is called from `paint()` whenever the new screen isn't `shape`, and on `pagehide` — check both still hold if you touch the router, or the camera light stays on after leaving the game.
- **Camera failure is never fatal.** `HT.state` (`idle`/`loading`/`ready`/`denied`/`insecure`/`error`) drives an overlay panel, and mouse/touch (press = grab) and keyboard (arrows + space) always work. Input priority in the loop is camera → keyboard → mouse, and using one clears the others' `on` flag.
- `vercel.json` deliberately does **not** set `Permissions-Policy`. The default already restricts cross-origin frames, and a malformed value would silently kill the camera in production where it's hard to debug.

### Level-1 adaptation is a separate engine

`SC.shape` does **not** touch `H.trials`/`H.engine` — those are force-domain (GSI/GAS/GES are meaningless for a reach task, and injecting values would pollute the clinician dashboard). Instead `reachEngine()` lazily builds `H.reach`, a `newEngine` over `target_size`/`directions`/`reps` seeded from `p.ability` by `reachStart()`, stepped by the same `updateEngine()` via the optional second argument (`PRIORITY_REACH`). Trials land in `SH.trials`; only the ok/fail bit is pushed to `G.results` so the existing reward screen works. Note `loadProfile()` reassigns `H` wholesale, which resets `H.reach` — intentional, but don't be surprised by it.

`target_size` is a **% of stage height**, mapped to a radius by `radiusOf()` (26% → 46px, 8% → 18px). `SLOT_R` (50) must stay larger than the biggest radius, otherwise the art reads as posting a big shape into a small hole.

## Known active inconsistency: FSR sensor count

The number of force sensors (FSR) is currently **inconsistent across the codebase** — this is a real, unresolved data-integrity issue (not hypothetical), tracked in `docs/SETUP.md` §3 and Prompt 2:

- `app.js` text/UI says **12** sensors in several places (`heat()` section, `METHODS` GDI description, Level 5 "Magic Garden" description, line ~1037, ~1060).
- The GDI formula in `METHODS` uses `H_max = log(12)` (~line 927), tied to a 12-slot `heat()` visualization (ring layout).
- The actual hardware has **6** sensors clustered on the finger-contact side (not a ring around the ball).
- `docs/hardware.md` (referenced in SETUP.md as the planned home for the real spec) does not exist yet in this repo.

If asked to fix sensor counts, `docs/SETUP.md` §"Prompt 2" has the exact required edits (text strings, the `log(12)`→`log(6)` formula change, and reworking `heat()` from a ring layout to a clustered layout since sensors don't surround the ball). Don't assume "12" is authoritative anywhere in `app.js` — verify against intent before propagating it.

## Language / audience notes

- UI copy and code comments are in Thai; `index.html` sets `lang="th"`. Keep new user-facing strings and comments consistent with the existing Thai copy unless told otherwise.
- **Design system (child face):** an outdoor adventure scene, not a website — sky gradient on `body`, plus a fixed `.scene` layer in `index.html` holding the sun mascot (`#i-mascot`), drifting clouds and grass hills (`display:none` on the pro face). Cards are white with 4px white borders and hard offset shadows (`--pop`/`--pop-2`) for a game feel. Tokens: `--sun`/`--grass`/`--grape`/`--berry`/`--aqua`, each with a `-soft`/`-deep` pair. **Prompt** (`--fd`) headings, **IBM Plex Sans Thai** (`--fb`) body. The pro face keeps its clinical `--pro-*` palette; don't leak child tokens into `dash`/`editor`.
- **`SC.landing` is the entry screen** (`S.screen` starts at `'landing'`): hero copy left, product shot right, CTA into `login`. Its image `rehaball.png` is a **derived asset** — a transparent cutout made from a 3D render by corner flood-fill; there is no source file in the repo, so regenerate it from a fresh export if it ever needs changing.
- **The sun mascot is inlined in `index.html`, not `<use href="#i-mascot">`** — `<use>` clones into a shadow tree, so the pupils can't be addressed. The `eyesFollowCursor()` IIFE at the bottom of `app.js` binds once (the mascot lives outside `#root`, so `render()` never replaces it) and writes `transform` straight from the pointer handler rather than via `requestAnimationFrame`, because rAF is suspended while a tab is hidden and would leave the eyes frozen.
- Clouds need the nested `<i>`: `.cl` carries the horizontal `drift` and `.cl i` the vertical `wave`. Two animations can't both drive `transform` on one element, so the layers must stay split.
- **The level map (`SC.home`) is the centrepiece.** `ROAD` holds 8 stop coordinates in a `1000x380` viewBox; `smoothPath()` (Catmull-Rom → cubic bezier) draws a road that passes exactly through them, and stops are placed with those same coords converted to percentages — so everything scales together. `mountRoad()` (called from `render()`) animates the kid's avatar along the road by sampling the **real** `<path>` with `getPointAtLength`, which is why it tracks the curve at any size. Don't switch this to CSS `offset-path`: that takes CSS pixels, not SVG user units, so it drifts as soon as the container isn't exactly 1000px wide. Level detail, goal, adaptation and other modes all live in the single `.quest` card below the map.
- **No emoji in the UI — this is deliberate, don't reintroduce them.** Every icon comes from the SVG sprite of `<symbol>`s at the top of `index.html`, rendered via the `ico(name, extraClass)` helper in `app.js` (`<svg class="ic" viewBox="0 0 24 24"><use href="#i-name"/></svg>`). Emoji were removed because they overflow their line box (a 60px box rendered a 69px glyph), render differently per OS, and read as machine-generated. Icon keys live in the data itself: `LEVELS[].em`, `MODE_META[].em`, `SKILLS[].icon`, `DIMS[].ico`, `AVATARS`. Add a `<symbol>` before referencing a new name.
- `AVATARS` are icon keys (`star`, `moon`, …), but profiles saved in `localStorage` before this change hold emoji — `AV_OLD`/`avKey()` migrate them on read. Always pass avatars through `avKey()`.
- Three things bite when editing this UI:
  - **Thai has no spaces between words**, so a long label will not wrap and will punch out of its container. `body` sets `overflow-wrap:break-word` globally and `.station b` adds `overflow-wrap:anywhere`; keep that in mind for any new fixed-width box.
  - **Thai needs generous `line-height` (~1.4+)** — upper vowels and tone marks stack above the baseline and collide with the line above at tighter values.
  - **Scope descendant selectors that target `svg`.** `.skilltree svg{position:absolute;inset:0}` silently matched every inline icon and stretched them across their parent; it must be `.skilltree>svg` (same for `.gamewrap>svg`).
  - **Child and pro share one stylesheet, so class names collide.** The child "recommended" card modifier was `.rec`, which the pro dashboard also uses for recommendation rows (`padding:12px 0`) — defined later, so it won won and silently killed the card's horizontal padding, pushing text to the border. It's now `.reco`. Prefix new child-face modifiers rather than reusing short generic names.
  - **A `max-width` on a centred block shifts its text off-centre.** `.kh` is capped at `60ch`, so on `.center` screens the heading centred inside that narrower block and sat ~80px left of the cards below it. `.center .kh{max-width:none;margin-inline:auto}` fixes it — watch for this whenever a constrained block sits above a wider one.
  - **White text on the light sky fails contrast** (measured 1.52:1). Headings on the scene use `--ink` with a white text-shadow; `.eyebrow` is a solid `--grape` pill with white text. Verified: h1/body/footer/logo 7.97:1, eyebrow 4.86:1, play button 7.37:1, "next" bubble 4.9:1.
- Motion (cloud drift + wave, mascot bob, sun-ray spin, ball float, stop pop-in, current-stop pulse, the traveller's journey, the page wipe) is all disabled under `prefers-reduced-motion`, and the clouds carry static fallback positions.
  - **To preview the motion without changing an OS setting, load `?motion=1`** (`?motion=0` clears it; the choice persists in `localStorage` under `rehaverse.motion`). It sets `html[data-motion="on"]`, which the reduced-motion block excludes via `html:not([data-motion="on"])`. Real users' preferences are still respected by default — don't "fix" a report of missing animation by deleting the media query.
  - Note that CSS animations are also **paused in hidden/background tabs**, so automated checks through a non-visible tab will read frozen `transform` values even when everything is configured correctly. Verify by comparing the computed offset against the animation's negative delay rather than by sampling movement over time.
- Screen changes route through `render()`, which plays a curtain over `#wipe`: it sweeps in, swaps the DOM behind it via `paint()`, then sweeps out. It uses `setTimeout` rather than `animationend`, because with animations disabled the event never fires and the swap would hang. `paint()` is the plain no-transition render — call that directly if you need an instant redraw.
  - Five styles (`curtain`, `iris`, `doors`, `blob`, `stripes`) and five tints are picked at random per navigation via `pickNot()`, which never repeats the previous choice. The style becomes a `s-<name>` class on `#wipe` and the colour a `--tint` custom property; `#wipe` holds two panels (`.p1`/`.p2`) since `doors` and `stripes` need a pair. To add a style, add its `.wipe.s-x` rules plus `.in`/`.out` keyframes and push the name onto `WIPE_STYLES`.
- The landing render is a photoreal image on a flat-vector page, so it's integrated deliberately: a stack of eight `drop-shadow()` passes traces a white sticker outline around the alpha (baking it into the PNG would work too, but this stays tweakable), with a rotating dashed ring and flat confetti behind it in `.artbg`. `.artwrap` exists purely to size a positioning context to the image so that backdrop can centre on the ball rather than the column.
- Contrast is verified, not eyeballed: body 5.9:1, eyebrow 4.9:1, the 9.5px `LEVEL` label 5.2:1, footer 4.6:1, primary button 5.5:1. `--primary` and `--ink-3` are tuned specifically to clear 4.5:1 on `--bg`, so darken rather than lighten them.
- The UI has two "faces" toggled via `document.body.dataset.face` (`child` vs `pro`) — screens under `dash`/`editor` are the caregiver/clinician-facing "pro" view; the rest are the child-facing view. Keep this distinction in mind when editing copy or styling — tone and information density differ deliberately between the two.
